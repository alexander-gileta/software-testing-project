# Отчёт: нагрузочное тестирование REST API Restful-Booker

## 1. Цель и окружение

Цель — оценить поведение трёх операций REST API при базовой и повышенной нагрузке, сравнить задержки, пропускную способность и ошибки.

- Тестируемый сервис: [Restful-Booker](https://github.com/mwinteringham/restful-booker), исходный код из предоставленного архива.
- Развёртывание: Docker Compose, сервис на порту `3001`.
- Генератор запросов: **k6** в отдельном Docker-контейнере с общей сетевой средой API.
- Целевой адрес для k6: `http://localhost:3001` (внутри общей сетевой среды контейнеров).
- Состояние данных: при каждом запуске контейнер API создаётся заново; сидовые бронирования восстанавливаются, накопленные POST-запросы обнуляются.
- Отчёт сформирован: 2026-10-18 16:21:06 UTC.

**Статус:** запуски в текущей среде не выполнены; числовые результаты отсутствуют.

## 2. Профиль нагрузки (определён до тестирования)

| Операция | Метод и endpoint | Доля запросов | Назначение |
|---|---|---:|---|
| Список бронирований | `GET /booking` | 50% | Частое чтение списка |
| Конкретное бронирование | `GET /booking/:id` | 30% | Чтение карточки по существующему ID |
| Создание бронирования | `POST /booking` | 20% | Изменение данных (запись) |

Профиль ориентирован на чтение (80%) с умеренной долей создания данных (20%). ID для чтения выбираются из начального набора существующих бронирований, чтобы не создавать искусственные 404. Фактические доли могут немного отличаться от заданных из-за случайного выбора операции.

| Параметр | Запуск 1: базовый | Запуск 2: повышенный |
|---|---|---|
| Тип модели | Закрытая, ramping VUs | Закрытая, ramping VUs |
| Одновременные виртуальные пользователи | 0 → 10 → 10 → 0 | 0 → 40 → 40 → 0 |
| Ramp-up | 0–30 с | 0–30 с |
| Plateau | 30–120 с (90 с) | 30–120 с (90 с) |
| Ramp-down | 120–150 с (30 с) | 120–150 с (30 с) |
| Общая запланированная длительность | 150 с | 150 с |
| Пауза между операциями | 0,2–0,5 с | 0,2–0,5 с |
| Целевая интенсивность | до 10 VUs | до 40 VUs |

В closed-loop модели интенсивность выражается числом активных пользователей, а не фиксированным RPS. Фактический RPS зависит от времени ответа и пауз. При увеличении пользователей в 4 раза можно оценить масштабируемость приложения.

## 3. Критерии успешности (заданы до получения результатов)

1. `http_req_duration p95 < 500 мс` — 95% запросов должны выполняться быстрее 500 мс.
2. `http_req_failed < 1%` — доля HTTP-ошибок должна оставаться менее 1%.
3. `scenario_errors < 1%` — доля ответов, не прошедших проверку статуса и структуры, должна быть менее 1%.

Критерии применяются к **каждому** запуску. Для API проверяются не только коды HTTP, но и структура JSON-ответа. Времена — измерения k6, миллисекунды.

## 5. Анализ результатов и ответы на вопросы

1. **Как изменилось среднее время ответа?** Невозможно определить без результатов обоих запусков.
2. **Как изменились p95 и p99?** Не измерены.
3. **Появились ли ошибки?** Неизвестно без вывода k6.
4. **Выполнены ли критерии?** Пока не проверены.
5. **Есть ли деградация?** Пока нельзя установить.
6. **Самый медленный endpoint?** Нельзя определить без p95 по каждой операции.
7. **Можно ли установить причину деградации?** Нет, одних клиентских метрик недостаточно.
8. **Какие серверные метрики нужны для поиска bottleneck?** CPU и throttling контейнера, RAM/RSS, heap и частота/длительность GC, задержка event loop Node.js, длительность обработки каждого маршрута, размер коллекции LokiJS, время запросов к хранилищу, размер HTTP-ответов, активные соединения, сетевой I/O, число HTTP 5xx/4xx и логи ошибок. Также важна загрузка самого генератора k6.
9. **Общий результат.** Сопоставление нагрузок 10 и 40 VUs на одинаковом профиле позволяет проверить рост задержек и ошибок, но без серверной телеметрии невозможно уверенно назвать причину изменений.

### Гипотеза для дополнительной проверки

Исходный код использует **LokiJS в памяти процесса Node.js**. Каждое создание бронирования увеличивает коллекцию, а `GET /booking` формирует список существующих ID. Возможная гипотеза: рост коллекции и размера ответа повышает стоимость получения списка. Для проверки нужно сопоставить p95 `GET /booking` с числом записей, CPU, задержкой event loop, временем обработки маршрута и размером возвращённого JSON. Это гипотеза, а не установленная причина.

После запуска `run_all.sh` в этом разделе автоматически появится вывод на основе фактических метрик. Для анализа возможного узкого места понадобятся CPU, RAM, GC, event loop и метрики обработки API/коллекции LokiJS.
