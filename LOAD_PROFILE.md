# Профиль нагрузки Restful-Booker

## Операции

| Операция | Доля запросов | Обоснование |
|---|---:|---|
| `GET /booking` | 50% | Список бронирований запрашивают чаще остальных операций |
| `GET /booking/:id` | 30% | Просмотр подробностей существующего бронирования |
| `POST /booking` | 20% | Создание нового бронирования реже чтения |

## Схема тестирования

| Этап | Временной интервал | Базовый запуск | Повышенный запуск |
|---|---|---|---|
| Ramp-up | 0–30 с | 0 → 10 VUs | 0 → 40 VUs |
| Plateau | 30–120 с | 10 VUs | 40 VUs |
| Ramp-down | 120–150 с | 10 → 0 VUs | 40 → 0 VUs |

Один запуск — 2 минуты 30 секунд. Два запуска на одинаковом сценарии, но с четырёхкратным отличием максимального числа виртуальных пользователей. Модель закрытая, поэтому RPS заранее не фиксируется: фактическая интенсивность будет измерена инструментом k6. Каждая итерация выполняет ровно одну из трёх операций по вероятностному распределению с паузой 0,2–0,5 секунды. Создание бронирований увеличивает объём данных сервиса; перед каждым запуском сервер пересоздаётся для независимости экспериментов.

## Критерии успешности (до эксперимента)

1. Глобальный p95 времени ответа < 500 мс.
2. Доля HTTP-ошибок < 1%.
3. Доля ответов с некорректным статусом или JSON < 1%.

Основные метрики: общее количество HTTP-запросов, RPS, среднее время ответа, p95, p99, доля ошибок, а также время ответа и доля ошибок отдельно для каждого endpoint.
